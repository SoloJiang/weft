# Weft 容器架构：宿主槽位（2026-08-16）

管容器：Weft 的表面挂在窗口的哪一块、那一块归谁、几何怎么算。
不管产品形态——那是 `2026-08-16-weft-third-mode-design.md`（canonical）。
不管编排：weftd store、thread_binding、bus、worktree 一律不动。

取代 `codex/native-right-panel-container` 分支上的
`docs/specs/2026-08-13-host-slot-layout.md`（PR #68，未合入）。那份文档的容器
判断成立并在此保留；它的产品判断「Weft 是 filter 不是第三模式」已被 08-16 spec
否定，此处剔除。它假设的 iframe 与「右侧是一块谁占谁的单槽」也都已过时，此处
按 build 6662 实测重写。

## 1. 问题

容器层把三件不同的事揉成一根 `mode × view` 轴：产品过滤、主区所有权、原生
chrome 所有权。而实现上只做了两件事：用 CSS 把原生列表藏掉，再把 Weft 表面盖
上去。

**根因不是少一块 UI，而是 host 没有窗口管理，只有隐藏和覆盖。**

这条诊断至今有效。2026-08-16 修掉的三个 bug 都是它的直接后果：workspace 铺满
`main` 压住原生底栏与右侧面板；看板视图上方挂着上一条线程的原生标题；同文档壳
之后两个 `/` 监听同时响应。

## 2. 判断

1. **Weft 是第三种模式**，与 Work / Codex 并列。不降级为 filter。
2. **host agent 是窗口管理器。** 它给每个槽位指定唯一 owner，按 owner 挂载或
   让位。**Weft 绝不绘制自己未拥有的槽位。**
3. **优先扩展宿主 chrome，而不是画平行容器**——但只在宿主留了扩展位的地方。
   模式菜单可以插第三项；右侧 tab 条不行（§5 实测）。宿主没留位置时，退到自己
   拥有的槽里绘制，**不要靠覆盖硬挤进去**。
4. **几何只从可见 DOM 实测。** 不写死尺寸；测不到当 0。
5. **减法失败 = 不能进 Weft**（08-16 spec §4）。但「减法」只涵盖功能性锚点，
   纯配色 token 缺失不在此列，理由见 `docs/compat/codex-builds.md` §8.2。

## 3. 槽位（build 6662 实测）

| 槽位 | 宿主锚点 | 允许的 owner | 现状 |
|---|---|---|---|
| `chrome` | `header[data-pip-obstacle="app-shell-header"]`，自身即拖拽区 | 永远 `native` | 已让位；workspace 下藏掉残留线程标题 |
| `nav` | `[data-app-action-sidebar-scroll]` | `weft` / `native` | 已落地 |
| `stage` | 可见 `main`，扣除 inspector 与 dock | `weft-workspace` / `native-thread` | 已落地 |
| `right` | `[data-app-shell-focus-area="right-panel"]` | **tab 容器**，见 §5 | 未落地 |
| `dock` | `[data-app-shell-focus-area="bottom-panel"]` | 永远 `native` | 已让位 |
| `overlay` | Weft 自建 root | `weft` | 已落地 |

两个 `focus-area` 锚点**按需渲染**：Codex 没打开过侧栏或底栏时，整个属性在文档里
一次都不出现。第一次探到空数组不等于锚点消失——同 `codex-builds.md` §2.2 记的
模式菜单。它们一旦创建就留在 DOM，关闭时塌成 inline `width/height: 0`。

## 4. 表面怎么挂

PR #72 之后是**同文档 shadow**，不是 iframe。三个 root 挂在宿主文档里，各自
`attachShadow`，共用一份 adopt 进去的 CSS。

这比 iframe 简单：不需要 host-context 跨帧协议，宿主 CSS 变量自动继承进 shadow，
Weft 表面之间也不必再靠 postMessage 对话。代价是**共用一个 `window`**——`/`
监听曾因此一次开两个搜索面，那一类接缝要按同文档重新检查。

新增表面就是第四个 shadow root，不是第五个 iframe。

## 5. 右侧面板是 tab 容器，不是单槽

6662 上 `[data-app-shell-focus-area="right-panel"]` 里有
`data-app-shell-tabs` / `tab-strip-controller` / `tab-controller` /
`tab-panel-controller`，四个原生 tab：Review ⌃⇧G、Terminal ⌃`、Browser ⌘T、
Files ⌘P。tab 条是 dnd-kit 可拖拽排序列表。

因此**不存在「占用右侧面板」这件事**。08-13 文档 §6 花大篇幅设计的「Weft 详情 /
Chats / Diff 三者互斥、共用一颗 Toggle、共用一条拉伸条」，前提已经不成立——宿主
自己把这块地做成了多 tab 容器。

曾以为正确做法是往 tab 条插一个 Weft tab，与模式菜单插第三项同一个模式。
**实测否定了这条路。**

注入本身没问题：克隆原生 tab 注入后，能在原生 tab 自身重渲染（终端标题变化）
之后存活，整个侧栏面板关闭再打开也还在，外观与原生一致。

但它**永远无法成为选中项**。2026-08-16 实测：注入一个 Weft tab，用真实指针点击，
宿主状态纹丝不动——它自己的 `diff` tab 仍是 `aria-selected="true"`，panel 也没换。

原因在宿主的模型里：

| 观测 | 结论 |
|---|---|
| tab id 是固定一套：`diff`、`browser`、`files`、`terminal:<uuid>` | 没有扩展位，宿主不认识第五种 tab |
| 两个 tab 时**只有一个 panel**，非选中的那个整个移出 DOM | panel 由选中态驱动渲染，不是隐藏 |
| 点注入的 tab 后选中态不变 | 选中由宿主 store 决定，DOM 里插节点进不去 store |

要让 Weft 内容在那里显示出来，只剩一条路：盖住宿主的 panel，同时让两个 tab 同时
画成选中。**那正是本文档 §1 要根除的「隐藏与覆盖」**，因此不做。

模式菜单能插第三项，是因为它是按需渲染的瞬时菜单、且我们点完第三项后立刻接管
整个模式；tab 条是常驻的、store 驱动的持久容器。两者不可类比。

## 5.1 详情分栏走 Weft 自己的 stage

既然右侧槽进不去，详情就留在 Weft 拥有的槽里：**stage 内部左右分栏**，看板在左、
issue 详情在右。产品诉求照样满足——点看板卡片时人留在看板上，详情从右侧出现——
而且不违反任何一条容器原则：Weft 只在自己拥有的槽里绘制，宿主的 `right` 与
`dock` 完全不碰。

代价写明：这与「用宿主原生侧滑承载详情」不是一回事。宿主没有给出可扩展的右侧槽，
在它开放之前，自绘一个属于自己 stage 的抽屉是唯一不靠覆盖的选择。宿主哪天开放了
扩展位，这一层可以整体搬过去——所以详情内容与它所在的容器要保持可分离。

### 5.1.1 形制照抄宿主的分栏（实测）

宿主自己就有一个可拖拽的右侧分栏，它怎么做我们怎么做：

| 项 | 宿主实测 | Weft |
|---|---|---|
| 宽度的表达 | inline `width: 765px`，用户拖拽后持久化 | 同左，持久化进 `desktop-host.json` |
| 拖拽手柄 | `role="separator"`，16px 命中区跨在边线上（`w-4 -translate-x-2`），`cursor: col-resize` | 同左 |
| 边线 | **没有描边线**。1px 内线常态透明，边界只由投影表达 | 同左 |
| 边缘投影 | `rgba(0, 0, 0, .18) -8px 0 16px -8px`（向左的方向性投影） | 同左，进 DESIGN.md 阴影表 |
| 层级 | 面板 `z-index: 41`，手柄 `z-40` | 用 Weft 自己的层级变量，相对关系一致 |

**默认宽度不照抄。** 宿主那 765px 是 Review/diff 面板的默认，为代码差异准备的；
issue 详情是文字。默认 420px、下限 320px、上限 stage 的 60%——**这三个是 Weft 的
选择，不是实测值**，落地后按真机观感再调。

### 5.1.2 窄了怎么办：关掉，不是挤扁

实测宿主在窗口收窄时的行为（`Emulation.setDeviceMetricsOverride`）：

| 窗口 | main | 右侧面板 |
|---|---|---|
| 1540 | 1265 | 765 |
| 1200 | 925 | 510 |
| 1000 | 725 | 360 |
| 900 | 625 | **不存在** |

两条规则：

1. **两栏一起缩。** 面板吃掉宽度变化的约 75%，主区吃 25%。不是「主区固定、面板
   自适应」，也不是反过来。
2. **窄到底就关掉次要面板**，不挤成一条、不改成覆盖层。消失点落在 main 725（还在）
   与 625（没了）之间。

第 1 条照搬。**第 2 条不照搬**——落地时发现方向反了：宿主关掉的是「你先前开着、
此刻没在看」的面板；而这里的详情是用户**刚点卡片要看的东西**，把它收起等于把这次
点击作废。

Weft 的规则改成：stage 跌破下限时**详情占满 stage、看板让开**。这既保住了点击的
意义，也正好退回改动前的整页行为，standalone 预览因此不需要额外的能力标志。

两种情况都是布局行为，不改路由——stage 重新变宽，分栏自动回来。

实测（stage 宽度 → 形态，`SPLIT_FLOOR = 720`）：

| stage | 形态 | 看板 | 详情 |
|---|---|---|---|
| 1265 | 分栏 | 845 | 420 |
| 925 | 分栏 | 505 | 420 |
| 725 | 分栏 | 305 | 420 |
| 685 | 详情占满 | 隐藏 | 685 |

回到 1265 自动恢复分栏，无粘滞。

### 5.1.3 交互契约

| 动作 | 结果 |
|---|---|
| 点看板卡片 | 详情打开并显示该 issue；人留在看板 |
| 点另一张卡 | 详情换内容，不关不重开 |
| 点同一张卡 | 保持打开（不做 toggle——toggle 会让「再看一眼」变成关掉） |
| 详情里点「打开对话」 | 切原生线程，stage 让给原生聊天，详情收起 |
| 切 workspace | 详情收起 |
| 切出 Weft | 详情收起，stage 整体卸载 |
| Esc / 详情头部关闭控件 | 详情收起，看板占满 |
| 宿主开右侧面板或底栏 | stage 收窄，两栏一起缩；不够宽就按 §5.1.2 收起详情 |

详情内容原样复用 `IssueDetailView`，去掉「返回看板」——分栏里看板一直在，没有
「返回」这回事，改成关闭。

standalone 浏览器没有 stage 概念，保留整页 `view=issue` 作为降级。

## 6. 会话数据按原生对齐

**决定（2026-08-16）：issue 的会话数据不再由 Weft 在侧栏自绘。**

原意是把会话树与 issue 详情都放进原生右侧面板。§5 的实测否掉了那个落点——宿主
右侧槽没有扩展位。落点改为**详情抽屉所在的同一块 stage 分栏**：会话树跟着详情
走，不再占用侧栏的垂直空间。

「按原生对齐」在这里落成两件具体的事：

1. **不重复宿主已有的东西。** 打开一条会话仍然只有一种方式——点原生会话行，由
   `openThread` 落到宿主自己的线程表面。Weft 不做第二个聊天容器。
2. **Weft 只提供宿主没有的那一层：归属。** 哪条会话属于哪个 issue、谁是 Primary
   Lead、哪些是 fork——这是编排信息，宿主没有，Weft 提供。

**这会改动 08-16 spec §8.7**——它现在写着侧栏含「issue 树（Lead / Tasks /
fork）」。落地时同步修订，不要让两份文档各说各话。

**已落地**：侧栏的 `.sidebar-expanded-issue` 整块拆除，Lead 的主会话与 fork 迁进
详情栏的「会话」段（`LeadConversations`），产物列表一并迁入。

迁移时只搬了会话树的 Lead 一半。它原本的 Tasks 一半没有搬——详情栏本来就逐个列出
任务且每个都带自己的会话入口，再画一份就是一件事两个控件。

侧栏因此不再需要展开态：`activeIssueId` 已经同时覆盖「线程打开的 issue」与「详情
打开的 issue」两种情况，原来的 `expandedIssueId` 变成纯冗余，连同 6 个写入点一起
删除。

## 7. 几何（已落地）

```
stage.top    = 拖拽区底边
stage.left   = 0
stage.right  = right-panel 盒子宽度
stage.bottom = bottom-panel 盒子高度
```

量盒子即完整判据：面板没创建过读 0，创建后关闭也读 0，两种「读不到」都对应
「Codex 在这没占地方」。缺失即 0 是 fail-open 的正确方向。

面板带过渡动画，必须把面板本身喂给 `ResizeObserver`；只在 inline style 翻转那
一刻量一次，会把 workspace 冻在动画中间尺寸。

**藏原生元素一律 `visibility: hidden`，不用 `display: none`。** 拖拽区挂在
`<header>` 自己身上，而 `stage.top` 正是从拖拽区底边反推的；塌掉盒子会让 top
算成 0，workspace 直接滑到窗口控件底下。

| 点侧栏 issue 行 | 打开 Primary Lead，stage=thread | 已落地 |
| 点看板卡片 | 人留在看板，stage 内右侧滑出该 issue 详情 | **待落地**，现在是整页详情 |

| 切 workspace / 切出 Weft | 收起 stage 内的详情分栏 | 待落地 |

## 10. 验收

真机 build 6662，Weft 模式，隔离 profile 与 weftd：

1. 开底栏：workspace 底边停在目录条上方，「weft-codex / weft」切换可点。
2. 开右侧面板：看板被挤窄而非被盖住；拖分隔条时 workspace 同步跟随。
3. 看板视图：标题栏不显示上一条线程标题；切到 thread 视图后恢复。
4. 点看板卡片：人留在看板，stage 内右侧滑出该 issue 详情。
5. 详情打开时再开宿主右侧面板：三者（看板 / 详情 / 原生面板）同时可见且各自可用，
   没有任何一块被盖住。
6. 切出 Weft：详情分栏收起，原生右侧面板与 tab 条完全未被改动过。

1–3 已通过（PR #89）。4–6 随 §9 步骤 4–5 落地。第 5 条是这套设计的真正考题——
它同时检验「Weft 只在自己的槽里绘制」与 §7 的让位几何。
